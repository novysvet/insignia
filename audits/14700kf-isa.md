# Intel Core i7-14700KF ISA audit for GLM-5.3 Flash inference

Date: 2026-08-28

Target: `glm-box`, Intel Core i7-14700KF, Windows 11 + Arch under WSL2

Scope: CPU preprocessing, quantization/dequantization, routing, reductions,
expert offload, cache movement, and thread placement. The remote repository was
not modified during the probe.

## Bottom line

The 14700KF has one genuinely useful AI-specific CPU extension for Insignia:
**256-bit AVX-VNNI** (Intel's client documentation also calls it AVX2 VNNI).
It also has AVX2, FMA, and F16C. It does **not** expose AVX-512, AMX, native
BF16 arithmetic, native FP16 arithmetic, AVX-VNNI-INT8, or
AVX-VNNI-INT16. Intel ARK's `Intel DL Boost: Yes` therefore must not be read as
"this CPU has Xeon AMX/BF16." On this part it means the 128/256-bit VNNI dot
products described below. [Intel ARK identifies AVX2 and DL Boost on the exact
SKU](https://www.intel.com/content/www/us/en/products/sku/236789/intel-core-i7-processor-14700kf-33m-cache-up-to-5-60-ghz/specifications.html),
and Intel's Raptor Lake Refresh datasheet explicitly identifies
[AVX2 VNNI as the vector deep-learning extension](https://edc.intel.com/content/www/us/en/design/products/platforms/details/raptor-lake-s/13th-generation-core-processors-datasheet-volume-1-of-2/009/intel-avx2-vector-neural-network-instructions-avx2-vnni/?language=en).

The highest-value immediate actions are:

1. Compile the GLM host code for `raptorlake`; it is currently built without an
   x86 CPU target.
2. Remove Zen-3 logical-processor assumptions and benchmark separate
   latency-critical and background pools on the hybrid 8P+12E topology.
3. Build an AVX-VNNI CPU expert microkernel only as an explicit heterogeneous
   fallback/overlap experiment. VNNI cannot accelerate the current raw
   NVMe-to-pinned-RAM-to-GPU path by itself.
4. Keep routing on the GPU if possible. AVX2 can make the present CPU router
   much cheaper, but eliminating its D2H synchronization is a better ceiling.

The CPU ISA is not the primary bottleneck in today's GLM path. Expert misses
are dominated by NVMe reads, host-to-device transfer, and GPU execution.
AVX-VNNI becomes material only if Insignia executes some experts on the CPU or
performs a meaningful packed-weight transform there.

## What this exact PC exposes

Read-only probes were run over `ssh glm-box` inside the Arch WSL distro. The
machine reports Windows build `10.0.26100.9278`, WSL kernel
`6.18.33.2-microsoft-standard-WSL2`, CPU family 6/model 183, and 28 online
logical CPUs. All 28 virtual CPUs report the same CPUID flag set.

Relevant `/proc/cpuinfo`/`lscpu` flags:

```text
fma f16c avx avx2 avx_vnni bmi1 bmi2 popcnt abm
gfni vaes vpclmulqdq pclmulqdq sha_ni
clflushopt clwb erms fsrm waitpkg movdiri movdir64b
```

Conspicuously absent:

```text
avx512* amx* avx_vnni_int8 avx_vnni_int16 avx_ifma
avx_ne_convert cldemote
```

GCC 15.3's target dump agrees:

```text
g++-15 -march=native -Q --help=target
  -march=alderlake  -mtune=alderlake
  -mavx2 -mfma -mf16c -mavxvnni                 enabled
  -mavxvnniint8 -mavxvnniint16 -mavx512* -mamx* disabled

g++-15 -march=raptorlake -Q --help=target
  -march=raptorlake -mtune=raptorlake
  same relevant enabled/disabled ISA set
```

That result matches the current
[GCC x86 target definition](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html):
`alderlake`, `raptorlake`, `meteorlake`, and `gracemont` share an AVX2/FMA/F16C/
AVX-VNNI baseline. `-march=raptorlake` is safe for this dedicated executable;
`-march=native` is also safe on this machine but labels the virtualized target
as Alder Lake. Prefer the explicit, reproducible target.

### WSL topology warning

Windows correctly reports 20 physical cores and 28 logical processors, matching
the SKU's 8 P-cores plus 12 E-cores. WSL instead presents 14 homogeneous cores,
each with two threads. It does not expose the real hybrid topology to `lscpu`.
Consequently, a WSL affinity such as "LP 0..7 are P-cores" is not established by
the guest topology and must not be baked in without a measured mapping.

Intel documents that P-cores are high-frequency/high-IPC and hyper-threaded,
whereas E-cores are single-threaded and intended for scalable/background work.
The 14700KF has 8P+12E, 33 MiB LLC, 28 MiB aggregate L2, and a maximum advertised
dual-channel DDR5-5600 bandwidth of 89.6 GB/s. These are upper bounds, not a
measurement of the installed DIMMs. [Exact 14700KF specifications](https://www.intel.com/content/www/us/en/products/sku/236789/intel-core-i7-processor-14700kf-33m-cache-up-to-5-60-ghz/specifications.html).

Intel's hybrid-development guide says old physical/logical-processor assumptions
no longer hold, recommends using only as many worker threads as scale, puts SMT
siblings last, and warns that indiscriminate `SetThreadAffinityMask` use can
reduce performance by constraining Thread Director. It also recommends separating
SIMD-heavy critical work from memory-heavy/background work so the scheduler can
classify it correctly. [Intel hybrid architecture developer guide](https://www.intel.com/content/www/us/en/developer/articles/guide/12th-gen-intel-core-processor-gamedev-guide.html).

## Supported features that can matter

### 1. AVX-VNNI: the real AI instruction

The supported VEX-encoded instructions are:

- `VPDPBUSD` / `VPDPBUSDS`: groups of four **unsigned-byte x signed-byte**
  products, accumulated into signed 32-bit lanes, with optional saturation.
- `VPDPWSSD` / `VPDPWSSDS`: pairs of **signed-word x signed-word** products,
  accumulated into signed 32-bit lanes, with optional saturation.

A 256-bit `VPDPBUSD` consumes 32 byte pairs and updates eight i32 accumulators.
It replaces the older multiply-add-add sequence and, importantly, avoids the
intermediate signed-16 saturation hazard of `VPMADDUBSW`. The operation and
CPUID requirements are defined in the
[Intel instruction-set reference](https://cdrdv2-public.intel.com/774492/325383-sdm-vol-2abcd.pdf).
The compiler intrinsics installed on the remote are:

```cpp
_mm256_dpbusd_avx_epi32
_mm256_dpbusds_avx_epi32
_mm256_dpwssd_avx_epi32
_mm256_dpwssds_avx_epi32
```

This is most promising for a CPU NVFP4 expert path:

1. Expand each NVFP4/E2M1 code into a small signed integer exactly; fold any
   factor-of-two needed by half-step codebook values into the group scale.
2. Quantize each activation group to u8, or bias an s8 activation by 128.
3. Use `VPDPBUSD` for the group dot product.
4. If using biased s8 activations, subtract `128 * sum(weight)` per row/group;
   precompute those row sums with the cached packed expert.
5. Convert the i32 group accumulator to FP32, apply weight/activation scales,
   and accumulate FP32 output.

That preserves the NVFP4 weight representation and adds at most activation
quantization error. It does not require storing a newly lossy weight format.
The group scaling and nibble expansion, not the dot instruction, may become the
bottleneck, so the experiment must compare fused on-the-fly expansion against a
lossless byte-expanded host-cache representation.

Base AVX-VNNI does **not** provide signed-byte x signed-byte `VPDPBSSD`.
Those additional signedness combinations belong to AVX-VNNI-INT8, which this
machine does not expose. Xbyak's encoding reference cleanly separates the four
base VNNI operations from the later INT8 variants. [Xbyak AVX-VNNI encoding
documentation](https://github.com/herumi/xbyak/blob/master/doc/usage.md#selecting-avx512-vnni-avx-vnni-avx-vnni-int8-avx102).

### 2. AVX2 + FMA: FP32 and packed-format workhorses

AVX2 supplies 256-bit integer operations, gathers, permutations, and FP32 FMA.
Intel's Raptor Lake datasheet describes the 256-bit integer, FMA, and gather
capabilities and cautions that sustained AVX work can change operating
frequency. [Intel Raptor Lake AVX2 section](https://edc.intel.com/content/www/us/en/design/products/platforms/details/raptor-lake-s/13th-generation-core-processors-datasheet-volume-1-of-2/015/intel-advanced-vector-extensions-2-intel-avx2/).

Useful applications in Insignia:

- nibble extraction, sign/codebook mapping, and 32-byte-at-a-time NVFP4 unpack;
- FP8 E4M3 decode using masks/shifts plus F16C or a small LUT;
- FP32 RMS/reductions, approximate sigmoid, scale application, and accumulation;
- fixed-size router top-k scans using vector max/compare rather than allocating
  `scores`, `choice`, and `order` on every layer/token;
- background quantization/cache conversion when it can overlap GPU work.

For nibble/codebook expansion, benchmark `VPSHUFB` lookup against arithmetic
decode. Avoid assuming AVX2 gather is best; its latency can lose to register
shuffles for tiny tables.

### 3. F16C is conversion only

F16C provides `VCVTPH2PS` and `VCVTPS2PH`, converting IEEE FP16 to/from FP32.
It does not perform FP16 addition, multiplication, or FMA. Intel's SDM states
that general FP16 arithmetic arrived with AVX-512-FP16, whereas F16C supplies
conversion only. [Intel SDM FP16 discussion](https://cdrdv2-public.intel.com/835781/325462-sdm-vol-1-2abcd-3abcd-4.pdf).

This is useful for FP16 scale tables and for the existing FP8-to-half-bit-pattern
decode trick. It is not a half-precision CPU GEMM engine. Intel's optimization
manual also notes that FP16 storage can save bandwidth but conversion overhead
and locality determine whether it wins. [Intel Optimization Reference Manual,
F16C section](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf).

### 4. Hybrid P/E cores and Thread Director

This is likely more valuable than any secondary ISA extension:

- Put latency-critical routing, launch/control, and any CPU expert kernel on
  P-cores.
- Put O_DIRECT reader threads, speculative prefetch, cache accounting, and
  offline/lossless expert expansion on E-cores when doing so does not reduce
  SSD queue depth or steal memory bandwidth from a CPU expert kernel.
- Use one hardware thread per P-core before using P-core SMT siblings for a
  bandwidth-heavy VNNI GEMV. Add the 12 E-cores only while whole-token latency
  continues to fall.
- Keep SIMD compute and branchy I/O/control in separate pools. Intel Thread
  Director uses the instruction mix to advise the Windows scheduler.

The exact SKU advertises Thread Director, and Intel explains that it observes
runtime instruction mix and core state and feeds scheduling guidance to the OS.
[Intel Thread Director description](https://www.intel.com/content/www/us/en/support/articles/000097053/processors/intel-core-processors.html).

Because Insignia currently runs GLM under WSL2, first benchmark with no hard
guest affinity. A native Windows build could enumerate Windows CPU Sets and use
soft placement/EcoQoS for background readers; guest LP-number pinning is not a
substitute for that enumeration.

### 5. Smaller useful extensions

- BMI1/BMI2, `POPCNT`, and `LZCNT` can help compact bitstream/index operations,
  but straight AVX2 masks/shuffles are more likely to win in the bulk NVFP4
  decoder. Treat `PEXT/PDEP` as microbenchmark candidates, not assumptions.
- GFNI can perform affine bit transforms per byte and may help an exotic packed
  layout transpose. It is lower priority than `VPSHUFB` for a 16-entry FP4
  codebook.
- ERMS/FSRM improve `REP MOVSB` implementations. Let libc handle ordinary small
  copies before writing a custom AVX copy loop.
- `WAITPKG` (`UMONITOR`/`UMWAIT`/`TPAUSE`) may reduce waste in a spin-heavy
  worker pool, but it is an idle/wait feature, not a compute accelerator. Test
  it only if profiling shows wake latency or spinning is material.

## Tempting features that are unavailable or wrong for this path

| Temptation | Reality on `glm-box` | Decision |
|---|---|---|
| AVX-512 / AVX-512 VNNI | No `avx512*` CPUID flags | Do not compile or dispatch it |
| AMX-INT8 / AMX-BF16 / AMX-FP16 | No `amx*` flags | Xeon/Core Ultra techniques do not apply |
| Native BF16 dot product | Requires AVX512_BF16 `VDPBF16PS` or AMX-BF16; neither exists | Keep BF16 as storage, expand/compute FP32, or use GPU |
| Native FP16 arithmetic | F16C converts only; no AVX512-FP16 | Convert to FP32 or use GPU |
| Native FP8 / FP4 CPU tensor arithmetic | No such exposed client ISA | Decode/quantize in software, then AVX2/VNNI/FP32 |
| AVX-VNNI-INT8 signed/signed dot | `avx_vnni_int8` absent | Use u8*s8 plus correction, or baseline AVX2 |
| AVX-VNNI-INT16 extended signedness | `avx_vnni_int16` absent | Base signed-word `VPDPWSSD` only |
| `MOVDIR64B` as a faster memcpy | It is a direct-store primitive with special ordering/atomicity semantics, not a magic cached DRAM copy | Do not use for expert cache copies without a device-memory-specific reason |
| `CLWB` as cache eviction | It writes back dirty lines and may retain them | Not a decode cache-management strategy |
| `CLDEMOTE` | Not exposed in WSL CPUID | No guest use |
| GNA 3.0 | A low-power speech/noise-suppression accelerator with a constrained software path, not a general LLM matrix engine | Ignore for GLM |

Intel documents BF16 dot arithmetic as the AVX-512_BF16 `VDPBF16PS`
extension on Xeon-class parts, making the absence of that CPUID feature
decisive. [Intel BF16 instruction description](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-deep-learning-boost-new-instruction-bfloat16.html).
The SDM describes `MOVDIR64B` as a 64-byte direct store, and `CLWB` as a writeback
that may retain the cache line. [MOVDIR64B / CLWB instruction reference](https://cdrdv2-public.intel.com/671110/325383-sdm-vol-2abcd.pdf).
Intel describes GNA as a low-power continuous-inference accelerator aimed at
speech recognition/noise suppression, and OpenVINO has deprecated its GNA
plugin. [Intel GNA use case](https://www.intel.com/content/www/us/en/developer/articles/technical/machine-learning-hw-accelerators-web-platform.html),
[OpenVINO GNA deprecation](https://www.intel.com/content/www/us/en/developer/articles/release-notes/openvino/2023-3.html).

## Current Insignia mismatches

### The GLM WSL host build leaves the ISA unused

`build/glm53-gen.sh` invokes:

```text
/opt/cuda/bin/nvcc -ccbin /usr/bin/g++-15 ...
    -Xcompiler=-pthread ...
```

It supplies neither `-march` nor `-mtune`. The host portions of
`glm53_generate.cu`, the index readers, routing code, and thread/cache machinery
therefore do not get the dedicated Raptor Lake target. Add these as an A/B:

```text
-Xcompiler=-march=raptorlake -Xcompiler=-mtune=raptorlake
```

Then inspect host disassembly and benchmark end-to-end. The target enables the
ISA; it does not guarantee GCC will recognize an arbitrary dot loop as VNNI.
Use intrinsics in the dedicated microkernel when exact instruction selection
matters.

### Existing CPU affinity is Ryzen-specific

`include/insignia_cpu.hpp` says LP 0..5 are six physical Zen-3 cores and pins
workers accordingly. `src/streaming.cu` hard-codes `0xFC0` as the Ryzen SMT
sibling set. Those assumptions are invalid on a 20-core hybrid Intel part and
must not be reused. This CPU tier is not currently part of the GLM WSL target,
but it will become relevant to heterogeneous expert execution.

### The current GLM router is allocation-heavy CPU scalar code

`Runner::moe_multi` downloads all router logits, then per token allocates
`scores`, `choice`, and `order`, calls scalar `std::exp`, and performs
`std::partial_sort`. For decode-sized rows, an AVX2 fixed-array top-8 scan and
vector sigmoid would be much cheaper. However, the first experiment should be
a GPU top-k/router kernel that leaves only the eight IDs and weights to copy;
that removes synchronization/transfer and is a higher ceiling than merely
vectorizing the CPU work.

### Single-SSD mode still starts an unused second-drive pool

`ExpertStager::start_pool` always creates four main-drive readers and two
alternate-drive readers. With no alternate shards, the latter wait forever and
all submissions still use `notify_all`. This is not an ISA issue, but on the new
single-SSD PC it is easy noise to remove before CPU scheduling experiments.
Detect whether any shard is alternate; create only the active drive pool and
benchmark reader counts 2/4/6/8 on this SSD.

## Prioritized implementation experiments

Every experiment must report median decode ms/token, accepted speculative
tokens/round, prefill tokens/s, CPU utilization, expert I/O GB/s, H2D time, and
greedy-token/parity checks. Reject microbenchmark wins that do not improve the
end-to-end path.

### P0 — establish the CPU/I/O budget

Profile one scalar and one DFlash2 run with CPU samples/counters plus existing
expert-I/O/H2D timings. Split wall time into NVMe wait, H2D wait, GPU kernels,
router D2H/sort, and host scheduling. This establishes the Amdahl ceiling for
all ISA work.

Expected bottleneck: expert NVMe/H2D dominates; host instruction count is a
small fraction unless verification creates large routing unions.

### P1 — Raptor Lake compiler target

Add `-march=raptorlake -mtune=raptorlake` to host compilation, rebuild cleanly,
and compare exact same prompt/seed. Inspect the host executable for AVX2/FMA and
confirm no AVX-512/AMX instructions. Keep the change only with measured
end-to-end benefit and parity.

Expected bottleneck: most hot numerical work is CUDA, so this may be a modest
gain; it is nevertheless nearly free and enables later intrinsics cleanly.

### P2 — hybrid-aware pools, no Zen masks

For WSL, leave affinity open initially and sweep reader/CPU-worker counts rather
than equating `hardware_concurrency()/2` with physical cores. Test 4, 8, 12, 20,
and 28 workers for a standalone CPU kernel, but use the SSD's measured queue
depth for O_DIRECT readers. For a future native Windows path, enumerate CPU Sets
and soft-place critical SIMD work on P-cores and background readers/prefetch on
E-cores.

Expected bottlenecks: memory-bandwidth saturation, E/P work imbalance, P-core
SMT contention, excessive wakeups from `notify_all`, and WSL's virtual topology.

### P3 — eliminate or vectorize CPU routing

Preferred: perform sigmoid+bias+top-8+normalization on the GPU and copy only
eight IDs/weights. Fallback A/B: fixed stack arrays, AVX2 sigmoid/choice, and an
eight-best insertion network with deterministic tie ordering. Preserve the
current operation/tie semantics closely enough not to flip expert choices.

Expected bottleneck: CUDA synchronization/D2H latency, not 512 scalar sigmoid
operations. This is why GPU routing should be tested first.

### P4 — AVX-VNNI NVFP4 expert microkernel

Implement one fixed-shape, lossless-weight-decode prototype for the actual
`2048x4096` gate/up and `4096x2048` down matrices. Compare:

1. AVX2 baseline (`VPMADDUBSW` + `VPMADDWD` + `VPADDD`, with proven no
   intermediate saturation or a safe widened formulation);
2. AVX-VNNI `VPDPBUSD`;
3. on-the-fly nibble expansion versus byte-expanded cached experts;
4. one token and a paired/multi-token verification batch;
5. P cores only versus P+E, adding SMT last.

Measure effective weight GB/s, MAC/s, expansion cost, and FP32 scale/reduction
cost separately. Validate against the CUDA NVFP4 result and the NumPy reference.

Expected bottlenecks: host DRAM bandwidth (89.6 GB/s is only the CPU's maximum
specification), NVFP4 codebook expansion, per-group scale FMAs, output
reductions, and hybrid load balance. VNNI compute can be idle while waiting on
weights.

If the microkernel is competitive, schedule it only on expert misses where CPU
execution finishes earlier than NVMe+H2D+GPU, or execute a predicted expert on
CPU in parallel with GPU work. Do not globally move experts to CPU on the
strength of a cache-hot microbenchmark.

### P5 — packed-cache transforms

Prototype AVX2 `VPSHUFB`/mask-based NVFP4 expansion and FP8 decode when a record
enters the host tier. Cache the transformed representation only if the extra RAM
buys enough reuse to amortize conversion and doubled bytes. For pass-through
experts, keep raw O_DIRECT into pinned memory: the current packed fast path
already avoids a 13.5 MiB CPU memcpy.

Expected bottleneck: larger transformed records reduce host-cache hit rate and
increase DRAM traffic. This can easily erase the VNNI win.

### P6 — wait/cache ISA only after profiling

Test WAITPKG for persistent CPU workers only if spin time is material. Test
non-temporal stores only for write-only offline/cache transformations that are
not immediately reread by the CPU; include `SFENCE` and measure GPU DMA
interaction. Do not spend time on MOVDIR64B, CLWB, GFNI, or BMI2 unless a profile
identifies a matching hot operation.

### P7 — library/JIT decision

Use intrinsics first: the GLM shapes and quantization geometry are fixed, so a
specialized kernel has little runtime dispatch overhead. oneDNN is useful as a
correctness/performance comparator for u8/s8 matmul, but it does not natively
consume Insignia's NVFP4 record format. Xbyak supports VEX VNNI encodings and is
worth adding only if per-shape JIT specialization demonstrably beats compiled
templates. Adding a JIT before the VNNI microkernel proves value would be
premature.

## Expected impact by subsystem

| Subsystem | ISA opportunity | Likely ceiling |
|---|---|---|
| Decode expert cache miss | AVX has almost no effect on raw O_DIRECT + H2D | SSD, pinned-memory/DMA, GPU |
| Decode expert CPU fallback | AVX-VNNI can be substantial | DRAM bandwidth, unpack/scales, P/E balance |
| DFlash2 verification | Batched CPU routing and possible paired VNNI kernel | Expert-union I/O and GPU work remain dominant |
| Prefill routing | AVX2 helps scalar host selection | D2H sync and distinct-expert I/O; GPU top-k is better |
| FP8/NVFP4 cache conversion | AVX2/F16C/shuffle can help | Conversion amortization and expanded-cache capacity |
| Norms/reductions | AVX2/FMA | Already mostly GPU; transfer/launch overhead |
| Cache copies | ERMS/FSRM or non-temporal stores in narrow cases | Memory bandwidth; current packed direct path has no bulk CPU copy |

## Acceptance gates

- Preserve exact greedy IDs for the established parity prompt; for new CPU
  numerical paths, also report maximum error, relative error, and cosine against
  the independent NumPy/CUDA reference.
- Benchmark cold and warm expert-cache cases separately.
- Report medians and dispersion, not a single best run.
- Record CPU package power/frequency if an all-core AVX2/VNNI result regresses
  GPU clocks or SSD/H2D progress through system power/thermal contention.
- Keep AVX-VNNI behind CPUID/runtime or target-specific executable dispatch;
  never infer AVX-512/AMX from the phrase "DL Boost."
